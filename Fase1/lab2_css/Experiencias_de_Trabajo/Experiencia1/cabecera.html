Seguridad en APIs

Las APIs permiten la comunicación entre diferentes aplicaciones, servicios y sistemas. Debido a que manejan información y funcionalidades importantes, también representan una superficie que debe ser protegida frente a accesos no autorizados, abuso de recursos y errores de configuración.

El OWASP API Security Top 10 reúne riesgos importantes que deben considerarse al diseñar, desarrollar y evaluar la seguridad de una API.

¿Cómo trabajan las APIs?

Existen diferentes tecnologías y arquitecturas utilizadas para implementar APIs. Entre las estudiadas se encuentran REST, GraphQL, gRPC y SOAP.

[ REST ] Representational State Transfer - Roy Fielding, 2000

  • Arquitectura basada en RECURSOS identificados por URLs.
  • Usa verbos HTTP nativos: GET , POST , PUT , PATCH , DELETE .
  • Formato: JSON (ligero, legible por humanos, clave valor).

[ GraphQL ]

  • Un solo endpoint: /graphql para todo.
  • El cliente decide qué campos recibir (Query Language).
  • Elimina over-fetching y under-fetching .
  • Schema con tipos fuertes e introspección automática.
  • Operaciones: query (leer), mutation (escribir) y subscription (real-time).
  • Debilidad: complejidad en caché y problema de N+1 queries , donde el servidor realiza una consulta inicial y luego consultas adicionales para los elementos solicitados.

[ gRPC ]

  • Llamadas a funciones remotas como si fueran locales ( RPC )
  • Formato: Protocol BUffers (binario, ultracompacto)
  • REQUIERE HTTP/2: multiplexing, streams, header compression
  • Soporta 4 modos de streaming (unary, server, cliente, bidi)
  • Auto-genera código en 10+ lenguajes desde .proto
  • Usado en: microservicios internos, IoT, sistemas de alto rendimiento.
  • Debilidad: no funciona en browsers nativamente, no legible por humanos.

[ SOAP ]

  • Protocolo basado en XML con estructura Envelope/Header/Body
  • Formato: Protocol BUffers (binario, ultracompacto)
  • REQUIERE HTTP/2: multiplexing, streams, header compression
  • Soporta 4 modos de streaming (unary, server, cliente, bidi)
  • Auto-genera código en 10+ lenguajes desde .proto
  • Usado en: microservicios internos, IoT, sistemas de alto rendimiento.
  • Debilidad: no funciona en browsers nativamente, no legible por humanos.

OWASP API Security Top 10 - 2023

Los siguientes riesgos representan diferentes problemas relacionados con autorización, autenticación, consumo de recursos, lógica de negocio, configuración y administración de APIs.

API1:2023

Broken Object Level Authorization - BOLA

Aparece cuando una API trabaja con identificadores de objetos pero no verifica correctamente si el usuario autenticado tiene autorización para acceder al recurso.

Ejemplo: modificar el ID de un usuario en una petición para intentar acceder a información perteneciente a otra cuenta.

API2:2023

Broken Authentication

Ocurre cuando los mecanismos utilizados para identificar a los usuarios presentan fallas que permiten comprometer credenciales, tokens o mecanismos de autenticación.

Ejemplos: ataques de fuerza bruta, credential stuffing, problemas con JWT y reutilización de tokens.

API3:2023

Broken Object Property Level Authorization

Se relaciona con una validación incorrecta de las propiedades de los objetos que una API permite leer o modificar.

Puede provocar exposición excesiva de información o permitir modificaciones de propiedades que deberían estar protegidas.

API4:2023

Unrestricted Resource Consumption

Las peticiones realizadas a una API consumen CPU, memoria, almacenamiento y ancho de banda. Si no existen límites adecuados, estos recursos pueden agotarse.

  • Ausencia de rate limiting.
  • Archivos sin límite de tamaño.
  • Paginación sin restricciones.
  • Abuso de servicios SMS o correo.
API5:2023

Broken Function Level Authorization - BFLA

Aparece cuando una API no controla correctamente qué funciones puede ejecutar cada rol o tipo de usuario.

Ejemplo: un usuario regular consigue acceder a funciones administrativas destinadas exclusivamente a administradores.

API6:2023

Unrestricted Access to Sensitive Business Flows

Se produce cuando funcionalidades importantes para el negocio pueden utilizarse de manera automatizada y abusiva sin suficientes controles.

  • Compra automatizada masiva de tickets.
  • Abuso de programas de referidos.
  • Spam automatizado.
  • Abuso de cupones y descuentos.
API7:2023

Server-Side Request Forgery - SSRF

Ocurre cuando una API obtiene un recurso remoto utilizando una URI proporcionada por un usuario sin validarla correctamente.

Funciones como webhooks, carga de imágenes mediante URL e integraciones externas pueden convertirse en posibles vectores de este problema.

API8:2023

Security Misconfiguration

Las configuraciones incorrectas en servidores, frameworks o servicios que soportan una API pueden exponer información o aumentar la superficie de ataque.

  • CORS configurado incorrectamente.
  • Errores demasiado detallados.
  • Métodos HTTP innecesarios.
  • Swagger expuesto en producción.
  • Headers de seguridad ausentes.
API9:2023

Improper Inventory Management

Una organización puede mantener versiones antiguas, endpoints olvidados o APIs no documentadas que continúan accesibles y presentan controles de seguridad insuficientes.

  • Versiones antiguas de APIs.
  • Shadow APIs.
  • Endpoints de debug.
  • Servicios internos expuestos.
API10:2023

Unsafe Consumption of APIs

Ocurre cuando una aplicación confía excesivamente en información proveniente de APIs externas y procesa esos datos sin las validaciones necesarias.

Un servicio externo comprometido puede convertirse en un punto de entrada para afectar a los sistemas que consumen sus datos.

Controles de seguridad

Los riesgos estudiados muestran la importancia de aplicar controles de autenticación, autorización, validación de entradas y limitaciones sobre los recursos utilizados por una API.

  1. Verificar autorización antes de entregar recursos.
  2. Proteger correctamente tokens y credenciales.
  3. Aplicar límites al consumo de recursos.
  4. Validar la información recibida.
  5. Mantener actualizado el inventario de APIs.
  6. Eliminar configuraciones y servicios innecesarios.
  7. Controlar las funciones disponibles según cada rol.

⚠ Importante

La seguridad de una API no depende únicamente de ocultar sus endpoints. Es necesario controlar quién puede acceder a cada recurso, qué operaciones puede realizar y qué información puede leer o modificar.

Una API segura requiere autenticación, autorización, validación y monitoreo.
